# 要件定義（叩き台）：全ポケモン横断ランキング（仮称）

厳選チェッカーの派生アプリ。**同じ食材を持ってくる全ポケモンを母集団**にして、手持ちの個体が何位（上位何%）かを出し、「そのポケモンを厳選し続けるべきか、別のポケモンに切り替えるべきか」の判断に使う。
別リポジトリの新規アプリとして作る前提。この文書は新リポジトリに移すための叩き台で、§9 の未決事項に答えてもらえれば確定版にできる。

## 1. 背景と課題

- 厳選チェッカーは「**同じポケモンの中で**」の順位（無補正個体に対する比と、同等以上の確率）を出す。
- 食材タイプは、同じ食材でも複数のポケモンが候補になる（例：トマトを持つ最終進化形は約14種。ウツボット・レントラー・ダグトリオなど）。
- ウツボットの中で最上位でも、レントラーの上位3%に届かない可能性がある。その場合は厳選対象のポケモン自体の見直しが推奨されるが、今のアプリでは判断できない。

## 2. 目的

1. 手持ち個体の「狙い食材の1日あたりの個数」を、**同じ食材を持ってくる全ポケモンの全個体**の中で順位づけする（全体での上位%）。
2. ポケモンごとに「**1匹捕まえて、この値以上になる確率**（平均何匹に1匹）」を並べ、**どのポケモンを厳選するのが最も効率が良いか**を示す。
3. 厳選ポケモンの見直しを促す判定（例：「ウツボットの今の個体は全体で上位40%。レントラーなら上位3%の個体が平均X匹に1匹」）を出す。

## 3. 用語

| 用語 | 意味 |
|---|---|
| 個体 | ポケモン × 食材配列 × サブスキル × 性格の1通り |
| 絶対値 | 1日あたりの狙い食材の個数（エナジー評価は将来）。ポケモンをまたいで比べられる値 |
| 無補正比 | 既存アプリの順位の基準（同じポケモンの無補正個体に対する比）。**ポケモンをまたぐ比較には使えない** |
| 母集団 | 順位づけの対象全体。§5 で定義する |

## 4. スコープ

| 区分 | 内容 |
|---|---|
| MVP | 食材タイプ。狙い食材（例：トマト）を選び、全ポケモン横断で個数の順位・上位%・ポケモン別の確率を出す |
| 次 | 食材のエナジー評価、きのみタイプ（きのみの個数・エナジー）、記録の保存と一覧 |
| 検討 | スキルタイプ（性質上、横断指標の設計から要検討） |
| 対象外 | 育成日数（`exp/` の領分）、厳選チェッカーの置き換え |

## 5. 機能要件（MVP）

### 5.1 入力

- 狙い食材（全食材から1つ）。
- 手持ち個体：ポケモン、食材配列、レベル、サブスキル（開いている枠）、性格。入力方法・検証は厳選チェッカーと同じ。
- 条件：レベル（50/60/70/80）、いいキャンプチケット、ヒーラー、日中の受け取り、おてボのチーム効果。厳選チェッカーと同じ項目・既定値。**母集団と手持ち個体は同じ条件で評価する**。

### 5.2 出力

1. **全体での順位**：手持ち個体の絶対値が、母集団の中で上位何%か。
2. **ポケモン別の一覧**（狙い食材を持つ全ポケモン）：
   - そのポケモンで、手持ちの値以上の個体が出る確率（平均何匹に1匹）。
   - そのポケモンの無補正個体・理論上の最大値・上位1%値などの目安。
   - 並べ替えは「確率が高い順」を既定にする。
3. **見直しの判定**：今のポケモンより「手持ちの値以上が出る確率」が明らかに高いポケモンがあれば、その旨を表示（閾値は未決。§9）。
4. 値の分布の可視化（母集団の分布に手持ち個体の位置を示す）。

### 5.3 母集団の定義（最重要。§9 で決める）

- 母集団の個体は、(ポケモン, 食材配列, サブスキル, 性格) の組。既存エンジンが持つ出現率モデル（食材配列の出現率・サブスキルの色別抽選・性格25種等確率）で重みづけする。
- **ポケモンをどう重みづけるか**が結果を大きく変える。案：
  - 案A（推奨）：**ポケモンを均等**（各ポケモンの確率質量を同じにする）。「どのポケモンを選んでも同じ数だけ捕まえるとしたら」の順位で、見直し判断の趣旨に合う。
  - 案B：出現率で重みづけ（実際のフィールドでの出やすさ）。「ランダムに捕まえた個体」の順位になるが、データ出典が不安定で、見直し判断には直接効かない。
- **食材配列の範囲**：トマトを持つ配列は、AAA だけでなく、ポケモンによって一部のスロットだけトマトのもの（ABA など）がある。「狙い食材の個数」で比べるので、トマトを拾わない配列も母集団に含め、絶対値で順位づけする（含めない案との差は§9で決める）。
- 食材配列は手持ち個体に固定する案も用意する（「AAA の個体同士の順位」）。

## 6. 計算要件

- 絶対値 = 厳選チェッカーの「狙い食材の個数」計算（所持数・げんき・おてつだい時間・チーム効果を含む）の値。既存の分布は「無補正比 × 確率」の行なので、**ポケモンごとの無補正個体の個数を掛けて絶対値に直し**、全ポケモンの分布をマージして累積確率を作る。
- 整合：1ポケモンだけを母集団にしたときの確率が、厳選チェッカーの「同等以上の確率」と一致すること（回帰テストにする）。
- 同じ性能とみなす基準（相対 1e-7）は厳選チェッカーと同じにする。
- 検証：にとよんツールとの値の比較を、厳選チェッカーと同じ方式で引き継ぐ。
- 計算量：ポケモン約14 × 食材配列最大27 × 条件（Lv 4 × チケット2 ほか）× サブスキル・性格の数え上げ。厳選チェッカー側のエンジンと事前計算（`scripts/precompute-dist.mjs`）の仕組みが土台になる。膨大になるので、**事前計算を前提**にする（§7）。

## 7. 非機能要件

- スマートフォンで使う前提（幅・通信量・待ち時間は厳選チェッカーと同じ基準）。
- 静的サイト（GitHub Pages）。サーバーは持たない。
- 既定条件は事前計算して配信し、それ以外の条件はブラウザの Worker で計算する（厳選チェッカーと同じ構え）。
- ゲームの更新（新ポケモン・食材・サブスキルの変更）に、データの差し替えと再計算だけで追従できる。
- 値の根拠を出典つきで残す（RaenonX 等。厳選チェッカーの README と同じ）。

## 8. 既存アプリとの関係（リポジトリ分離）

| 項目 | 方針（案） |
|---|---|
| 計算エンジン | `js/calc.js`・`checker/js/engine.js`・`checker/js/ingredient/` などを共有部品にする必要がある。**案1**：新リポジトリにコピーして始め、差分は手で同期。**案2**：エンジンを共通ライブラリ（npm / git submodule）として切り出し、両アプリが使う |
| データ（ポケモン・食材・性格） | 共通ライブラリ側に置く。重複すると、ゲーム更新で片方だけ古くなる |
| 画面 | 新規。厳選チェッカーとは別のデザイン（共通にするかは §9） |
| 連携 | 厳選チェッカーから「全ポケモンで見る」のリンクで、ポケモン・サブスキル・性格を URL で引き継ぐ。逆も同様（`exp/` と同じ形） |

## 9. 未決事項（回答がほしいもの）

| # | 質問 | 推奨 |
|---|---|---|
| 1 | 母集団のポケモンの重みづけは均等か、出現率か（§5.3） | 均等（案A） |
| 2 | 狙い食材を拾わない食材配列を母集団に含めるか。AAA だけに絞るか | 含める（絶対値で比べるため）。AAA 限定は表示オプション |
| 3 | 評価の指標は MVP では個数のみでよいか（エナジーは次） | 個数のみ |
| 4 | MVP のタイプは食材だけでよいか（きのみ・スキルは次以降） | 食材のみ |
| 5 | 「見直し推奨」の判定の閾値（例：他ポケモンで同等以上が出る確率が今のポケモンの2倍以上） | 2倍を叩き台にし、使いながら調整 |
| 6 | エンジンの共有方法（案1 コピー / 案2 共通ライブラリ） | まず案1で始め、安定したら案2へ |
| 7 | アプリ名・リポジトリ名 | 未定 |
| 8 | 配布場所（GitHub Pages 同様か、別か）と、厳選チェッカーとのデザイン共通化 | GitHub Pages・デザインは共通の部品を流用 |

## 10. 次のステップ
