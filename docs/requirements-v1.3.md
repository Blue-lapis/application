# ver1.3 要件定義：スキルタイプの評価基準の見直し

[ver1.2](requirements-v1.2.md)（食材タイプの見直し）を土台に、スキルタイプの順位基準・げんきの考え方・パラメーター設定を見直す。今回はスキルタイプだけを対象とし、きのみタイプ・食材タイプの計算と画面は変えない。ver1.1 の「今後の予定」にある「食材タイプ・スキルタイプへのげんきモデル・受け取り設定の展開」のうち、スキルタイプの分にあたる。

実装後に、作りを `design-v1.3.md` にまとめる（[`design-v1.2.md`](design-v1.2.md) と同じ形）。

## 1. 背景

スキルタイプは ver1.0 のままで、食材タイプ（見直し前）と同じ問題が残っている。

- **げんきが悲観的すぎる**: 起床時100から回復なしで10分ごとに1減るだけ（または常に81%以上）。
- **おてつだい回数を整数で数えている**: 共通の `schedule` は日ごとの整数回を8日分平均する。きのみタイプ・食材タイプは小数（期待値）で数える。
- **最大所持数が捕まえた姿の値のまま**: 進化1回ごとの+5を足していない。睡眠中に満タンになる時刻が早すぎ、キューで抽選が止まるのが早い。
- **性格のげんき回復量補正を計算していない**。
- **おてつだいボーナスのチームへの効果を数えていない**: 自分のおてつだい時間の短縮としてのみ計算している。
- **日中は常にタップする前提**。

## 2. 評価の基準

### 2.1 順位の基準（発動回数 ＋ おてボのチーム効果）

食材タイプと同じ考え方にする。

```
順位の基準 = 自分の1日の期待スキル発動回数
          ＋（自分がおてつだいボーナスを持つとき）ほかの4匹が増やす発動回数
```

- ほかの4匹は **同じポケモン・サブスキルなし・無補正性格・同じパラメーター**。食材配列は入力しないので、自分と同じく配列の出現確率で平均する。
- 1匹あたりの増加分 = おてつだいスピード+5%（おてボ）ありの発動回数 − なしの発動回数。
- 無補正比の分母は無補正個体の発動回数（チーム分は0）。
- 「おてボのチーム効果」はきのみタイプ・食材タイプと共通の設定（既定は「含める」）。「含めない」なら自分の発動回数だけで比べる。
- 上位%の分布は、今と同じくサブスキルと性格25種を数え上げる。

### 2.2 検討の記録

新しいモデルでの試算（Lv.80まで、ヒーラー1匹・常にタップ・チケットあり、サブスキル1つだけの無補正比）:

| ポケモン | スキ確M | スキ確S | おてスピM | おてスピS | おてボ（自分だけ） | おてボ（＋4匹） |
|---|---|---|---|---|---|---|
| ミュウツー | 1.228 | 1.112 | 1.123 | 1.057 | 1.041 | 1.203 |
| ゴルダック | 1.304 | 1.154 | 1.132 | 1.063 | 1.044 | 1.222 |
| プクリン | 1.244 | 1.121 | 1.146 | 1.070 | 1.048 | 1.241 |
| デンリュウ | 1.274 | 1.136 | 1.131 | 1.063 | 1.044 | 1.220 |
| ウインディ | 1.282 | 1.140 | 1.126 | 1.059 | 1.041 | 1.203 |

- 並びは「スキ確M ＞ おてボ（＋4匹） ＞ おてスピM」で、食材タイプ（食材確率アップM ＞ おてボ ＞ おてスピM）と同じ形になる。
- 4匹分を含めないと、おてボはおてスピSより下になる。
- 採らなかった案: スキルレベルアップ・スキルの効果量で比べる（スキルごとに単位が違い、データ作りの手間が大きい）。

### 2.3 結果の表示

- 大きく出す値: 自分の発動回数（日中 / 睡眠中の内訳）。おてボ持ちで「含める」のときは、同じ枠に「おてボによるほかの4匹の増加 +○回」を出す。
- 性能の欄: 今の項目に、ほかの4匹の増加・無補正個体の発動回数・最大所持数（基礎＋進化×5＋サブスキル）を加える。

## 3. げんきのモデル

- きのみタイプ・食材タイプと同じモデル（ヒーラー・料理による回復・性格のげんき回復量補正・小数のおてつだい回数）を使う。
- 詳細ダイアログの「げんき（10分ごとに減少 / 常に81%以上）」は、共通のヒーラー・回復量・発動回数・おてボのチーム効果に置き換える。これで3タイプとも詳細の設定が共通になる。
- 性格の分類に「げんき回復」を加える（スキル・おてスピ・食材・げんき回復・なし他）。
- 自分のスキルによる回復（げんきチャージSなど）は扱わない。

## 4. 小数のおてつだい回数と天井カウンタ

- 天井カウンタの分布を日をまたいで追う形（`runDays`）は残す。
- 区間ごとのおてつだい回数が小数のときは、前後の整数回の結果を割合で混ぜる。天井の分布も混ぜたまま翌日に引き継ぐ。
- 計算時間が延びるので、ver1.2 と同じく5枠の分布の計算時間を測って記録する。

## 5. 所持数

- 最大所持数を「捕まえた姿の値 + 進化1回ごとに5」にする。`checker/js/skill/mons.js` に `evo` を加える（伝説・幻・進化しないポケモンは0）。
- 54匹の進化の回数を確かめて README の表に載せる。

## 6. 日中の受け取り

- 設定: **常にタップ / 3時間ごと**（食材タイプと同じ）。既定は **常にタップ**。保存キーは食材タイプと同じ `ckingtap` を共有するか、別にするかを実装時に決める。
- **常にタップ**: 今と同じ。日中はストックが発生せず、所持数を見ない。
- **3時間ごと**: 起床から3・6・9・12・15時間後と就寝時に受け取り、区間ごとに所持数0から追う。
  - 区間の中で満タンになった後は、睡眠中と同じ規則とする（キューに残る4回分まで抽選し、その後は抽選しない）。
  - 区間の中のスキルのストックは、睡眠中と同じく2回までとする（要確認: 起床中のストック上限の出典を確かめる）。

## 7. あわせて必要な対応

- `checker/js/skill/calc.js` を、共通の `energyCurve`・`helpsPerTap`（きのみタイプの `curveOf`・`timesMix`・`mixed`）を使う形に書き換える。これで共通の `schedule` を使うタイプはなくなるので、`js/calc.js` から外す。
- `runDays` を小数の回数と区間（受け取り）に対応させる。きのみタイプ・食材タイプは `runDays` を使わないので影響しない。
- `env` のスキルタイプの項目を `N`, `camp`, `mon`, `heal`, `healAmt`, `healTimes`, `tap`, `team` にする。保存済みの `g80` の設定は ver1.1 と同じ処理で「常に81%以上」として引き継ぐ。
- 分布の保存キーに新しい条件を加え、`MODEL_VERSION` を上げる（今は6）。
- きのみタイプ・食材タイプの結果が変わらないことを、変更前後の値の比較で確かめる。
- `tests/check-dist.mjs` にスキルタイプの新しい条件を加える。
- `checker/README.md` のスキルタイプの計算モデル・ポケモンの表、リポジトリ直下の `README.md` の共通の計算モデル（げんき・天井・ストック）を更新する。

## 8. 今回は扱わないもの

- スキルレベルアップ・メインスキルの効果量。
- チーム全体の発動回数による確率低下（スキルゲート）、フレンドメダルによる金枠確定。
- 自分のスキルによるげんきの回復、ほかのメンバーを別のポケモンに変えること。
