# ver1.9 要件定義：上位%の分布の事前計算（叩き台）

ver1.8（`77965e2`、PR #49）を土台に、既定の条件の上位%の分布を GitHub Actions のデプロイ時に Node で計算し、静的なファイルとして GitHub Pages に一緒に公開する。初めて開く人や別の端末で開いた人が、分布の計算を待たずに確率・順位を見られるようにする。作業ブランチは `claude/clever-goldberg-dz8brx`。

評価の規則と計算結果の値は変えない（`MODEL_VERSION` も上げない）。**この文書は段階1の叩き台で、対象範囲（§4）は未決定。** 決まるまで実装（段階2）には進まない。

## 1. 現状

### 1.1 分布の保存のキー

`checker/js/distcache.js` の `cacheKey(type, env)` は次を `|` でつないだ文字列。

| 部分 | 中身 | 変わるとき |
|---|---|---|
| `MODEL_VERSION` | 今は `10` | 計算方法を変えて手で上げたとき |
| `BUILD` | モジュールの URL の `?v=`（公開時に付くコミットの先頭8文字）。ローカル・Node では空 | **公開のたび** |
| `COMMON` | サブスキル・色の確率・性格・げんきの倍率・`slotWeights` の FNV-1a ハッシュ | 共通データを変えたとき |
| タイプ | `berry` / `ingredient` / `skill` | — |
| ポケモン | `MONS[mon]`（基礎値）のハッシュ | ポケモンのデータを直したとき |
| 条件 | `env` の全項目をキー順に並べた JSON | 画面の設定 |

- `env` はタイプごとに `{ lv, N, camp, mon, heal, tap, team, healAmt, healTimes }`。食材タイプだけ `target`（狙い食材 A/B/C）が加わる。`N` は `lv` で決まる（Lv.50・60 は3、70 は4、80 は5）。
- フィールドボーナス・好きなきのみ（ver1.8）は無補正比に効かないので `env` に入らない。
- `BUILD` が入っているため、**公開のたびに全員の IndexedDB の分布が使えなくなり、計算し直しになる**。「別の端末」だけでなく「前に開いた人」も、公開直後は待つことになる。

### 1.2 既定の条件

`checker/js/state.js` の既定値（保存値も URL の指定もないとき）。

| 項目 | 既定 | 選べる値 |
|---|---|---|
| レベル `lv` | 60（`N` = 3） | 50 / 60 / 70 / 80 |
| いいキャンプチケット `camp` | あり | あり / なし |
| ヒーラー `heal` | 1匹 | なし / 1匹 / 常に81%以上 |
| 日中の受け取り `tap` | きのみ: なし（`none`）、食材・スキル: 常にタップ（`always`） | それぞれ3時間ごと（`3h`） |
| おてボのチーム効果 `team` | 含める | 含めない |
| 回復量 `healAmt` | 18 | 整数 1〜150 |
| 発動回数 `healTimes` | 3 | 0〜20（小数第2位まで） |
| 狙い食材 `target`（食材） | そのポケモンで前回選んだもの、なければ A | ポケモンの食材の数（2〜3） |

- ポケモンは きのみ31・食材40（狙い食材を数えると119）・スキル54 で、分布の単位は **204**（以下「ポケモン単位」）。
- 画面は、今の条件の分布を計算した後に、**チケットのあり・なしを切り替えた条件も先に計算しておく**（`ui.js` の `requestDist`）。そのため、チケットは両方を用意しないと、開いてすぐ Worker が動く。

### 1.3 計算にかかる時間（実測）

この環境（Xeon 2.8GHz・4コア、Node 22）で、条件ごとに新しいエンジンを作って計算した時間（Worker と同じ）。3,264件を全部計算した。

| タイプ | Lv.50 | Lv.60 | Lv.70 | Lv.80 |
|---|---|---|---|---|
| きのみ（1件の最大） | 0.12秒 | 0.11秒 | 0.16秒 | 0.26秒 |
| 食材（1件の最大） | 0.20秒 | 0.31秒 | 0.53秒 | 0.86秒 |
| スキル（1件の最大） | 0.30秒 | 0.36秒 | 0.81秒 | 1.36秒 |

ヘッドレス Chromium の Worker（同じ PC、保存なし）でも、フライゴン Lv.60 が 0.31秒、Lv.80 が 0.74秒、ミュウツー Lv.80 が 0.54秒で、Node とほぼ同じだった。**PC では待ち時間は1条件あたり1秒未満**で、開いたときにチケットの両方を計算するので最大で2倍になる。スマートフォンでは数倍かかると見込むが、今回は実機で測っていない（DevTools の CPU 絞り込みは Worker に効かなかった）。

## 2. Node から計算コードを呼べるか

**そのまま呼べる。切り出しは要らない。**

- `checker/js/*/calc.js`・`engine.js`・`js/calc.js`・`js/constants.js` は DOM・`self`・`window` に触れない ES modules で、`tests/check-dist.mjs`・`tests/bench-dist.mjs` がすでに Node から `createEngine().dist(env)` を呼んでいる。
- `distcache.js` も Node で読み込める（`indexedDB` は使うときにだけ触る）。Node では `import.meta.url` に `?v=` がないので `BUILD` は空になる。
- 事前計算は Worker と同じく、1条件ごとに `TYPES[type].createEngine().dist(env)` を呼び、`clearCaches()` で途中の値を捨てる。計算の順番に結果が依存しないことは ver1.4 からの方針。

段階2で足すのは次の2つだけ。

- `distcache.js` に `BUILD` を除いたキー（`MODEL_VERSION|COMMON|タイプ|ポケモンのハッシュ|条件`）を返す関数を足し、事前計算のファイルの照合に使う。
- 同じファイルに、分布を事前計算のファイルの中身に直す関数と、その逆を置く（Node とブラウザで同じ関数を使う）。

## 3. 保存の形式

分布は無補正比 `r` と確率 `p` の行の並び（高い順）。行数は きのみ 160〜200、食材 4千〜2万、スキル 5千〜2.5万。

| 形式 | 抜き取り64件の合計 | 比 |
|---|---|---|
| そのままの JSON（`{ r: [...], p: [...] }`） | 24.6MB | 1 |
| 上を gzip | 4.7MB | 0.19 |
| `r` を差分の整数にした JSON | 20.2MB | 0.82 |
| **上を gzip（推奨）** | **3.5MB** | **0.14** |
| バイナリ（`r` の差分を可変長整数・`p` を Float64）を gzip | 3.0MB | 0.12 |

- `r` は `buildDist` で `toFixed(9)` を数値にした値なので、`Math.round(r × 1e9)` の整数から `n / 1e9` で同じ値に戻る（64件・73万行で全行ビットまで一致を確認）。高い順なので差は正の整数になる。
- `p` は丸めずに JSON の数値で持つ（`JSON.stringify` は倍精度を往復で失わない）。値を変えないため、`p` の桁は減らさない。
- バイナリは JSON の gzip より約15%小さいが、中身を目で確かめにくく、差が小さいので JSON にする。
- 1ファイルは `{ v: MODEL_VERSION, key: BUILD を除いたキー, env, r: [...], p: [...] }`。

**置き方の案**: gzip したファイル（`.json.gz`）を置き、画面では `DecompressionStream('gzip')` で戻す。GitHub Pages は `.gz` をそのまま（`Content-Encoding` なしで）返すので、公開物の大きさも転送量も gzip の大きさになる。`DecompressionStream` のないブラウザ（Safari 16.3 以前など）は、取得を諦めて Worker で計算する。gzip しない `.json` を置く方法もあるが、公開物の大きさが約6倍になる（§4 の「未圧縮」）。

## 4. 対象範囲の案

どの案も、ヒーラー1匹・回復量18・発動回数3・チーム効果を含める・チケットあり／なしの両方・食材タイプは全部の狙い食材を対象にする。サイズは §3 の推奨形式で3,264件を実際に作って測った値（ファイルの見出しの分を含む）。CI の時間は、この環境の CPU 時間の合計を4並列で割った見込み（GitHub のランナーは4コア。CPU の速さの違いで1〜2倍の幅を見る）。

| 案 | 範囲 | 件数 | 未圧縮 | gzip（公開物） | 1ポケモンを開いたときの取得 | CPU 時間 | CI の増加（見込み） | 待ち時間がなくなる場面 |
|---|---|---|---|---|---|---|---|---|
| **1** | Lv.60 だけ | 408 | 64MB | **12MB** | 食材 約80KB・スキル 約46KB・きのみ 約2KB（2ファイル） | 69秒 | +20〜40秒 | 初めて開いて既定のまま見る。ポケモンを切り替える。チケットを切り替える |
| 2 | Lv.50・60・70 | 1,224 | 235MB | **42MB** | 食材 最大約250KB・スキル 最大約130KB | 246秒 | +1〜2分 | 1に加えて Lv.50・70 に切り替える |
| 3 | Lv.50〜80 すべて | 1,632 | 485MB | **87MB** | 食材 最大約410KB・スキル 最大約250KB | 490秒 | +2〜4分 | 既定の設定のまま、どのレベルでも |
| 4 | 3＋日中の受け取り2通り | 3,264 | 995MB | **178MB** | 3 と同じ | 1,091秒 | +5〜9分 | 3に加えて受け取りを「3時間ごと」にした人 |

- 1ポケモンを開いたときの取得は「今の条件」と「チケットを切り替えた条件」の2ファイル。レベルを切り替えるたびに、そのレベルの2ファイルを取る。全件を一括では読まない。
- 1ファイルの gzip の大きさ（中央値 / 最大）: きのみ 1KB / 2KB、食材 40KB / 205KB、スキル 23KB / 126KB（案3）。
- 目安の「数十MB」に収まるのは案1・案2。案3は gzip で 87MB、案4は 178MB。GitHub Pages の公開物の上限（1GB）には、gzip ならどの案も収まる。
- ヒーラー（3通り）・チーム効果（2通り）まで広げると案4のさらに6倍（約1GB）になり、Pages の上限に近づくので候補にしない。回復量・発動回数は値が連続なので対象外。

### 推奨：案1（Lv.60 だけ）

- 目的の「初めて開く人・別の端末で開いた人」は、まず既定の条件（Lv.60・チケットあり）で見る。案1はこの場面と、ポケモン・チケットの切り替えを全部覆う。
- 公開物が 12MB・CI の増加が1分未満で、ワークフローへの影響が小さい。
- §1.3 のとおり、PC では1条件の計算が1秒未満なので、Lv.50・70・80 に切り替えたときの待ちは Worker の計算でも短い。取得（約40KB）と計算（0.3〜0.8秒）の差は、主にスマートフォンで効く。
- 範囲はスクリプトの1か所（レベルの一覧）で広げられるので、使われ方を見てから案2に広げられる。

案2は、Lv.50・70 もよく使うなら候補になる（42MB、CI +1〜2分）。

## 5. CI での作り方

| 方法 | 利点 | 欠点 |
|---|---|---|
| **A. 毎回計算（推奨）** | いつも今のコードで作るので、`MODEL_VERSION` の上げ忘れがあっても古い値を出さない。仕組みが単純 | 毎回 CPU 時間がかかる（案1で +20〜40秒） |
| B. `actions/cache` で使い回す | 計算に関わるファイルが変わらなければ計算を飛ばせる | キーを `MODEL_VERSION` だけにすると、計算のコード・ポケモンのデータを変えても `MODEL_VERSION` を上げないとき（ver1.6〜1.8 はどれも上げていない）に古い分布を出す。安全にするにはキーを `hashFiles('js/**', 'checker/js/**')` にする必要があり、公開の多くが js の変更なので、ほとんど当たらない |
| C. 生成物をコミットする | CI の時間が増えない | 案1でも 12MB の生成物が、計算やデータを変えるたびに履歴に積み上がる。作り直し忘れがあると古い分布を出す（画面のキーの照合で使われなくはなるが、事前計算の効果がなくなる）。PR の差分が読みにくい |

- ファイル側の `key` には `COMMON` とポケモンのハッシュが入るので、データの変更で古いファイルが**誤って使われる**ことはない。ただし `MODEL_VERSION` を上げずに計算方法を変えた場合は、キーが同じになるので区別できない。A はここを「毎回作り直す」ことで防ぐ（今の IndexedDB が `BUILD` で防いでいるのと同じ考え方）。
- 案1なら A の増加は小さいので A を推奨する。案3・4を選ぶ場合は、`hashFiles` をキーにした B を足すか検討する。
- 実行場所は、今の `test` ジョブの後（`deploy` ジョブの中、`Collect site files` の前）。`node:worker_threads` などで4並列にする。

## 6. 画面の読み込み（段階2の方針）

- 順番は「IndexedDB → 事前計算のファイル → Worker で計算」。どれも Worker の中で行う（`worker.js` は今 IndexedDB → 計算の順）。
- ファイルの場所は `checker/dist/<MODEL_VERSION>/<タイプ>/<ポケモン>/<条件>.json.gz` のように、条件から一意に決まる名前にする。名前に `MODEL_VERSION` を入れ、公開のたびに `?v=コミット` を付けて Pages のキャッシュ（10分）で古いファイルと混ざらないようにする。
- 対象外の条件（案の範囲外）は取得しない（範囲の一覧を画面側にも持つ）ので、404 を出さない。
- 取得したら `v` と `key` を今の値と比べ、違えば捨てて計算する。404・通信エラー・gzip や JSON の壊れ・行の数の不一致でも計算に進み、画面は止めない。
- 使った分布は今までどおり IndexedDB（`BUILD` 入りのキー）にも保存する。

## 7. 完了条件（段階2）

| 確認 | 条件 |
|---|---|
| 値の一致 | 事前計算のファイルから戻した分布と、Worker と同じ手順で計算した分布を比べ、行数・`r`・`p` がビットまで一致する（全件、少なくとも §4 の範囲すべて）。差が出たら浮動小数の誤差の範囲か報告する |
| ブラウザとの一致 | ヘッドレス Chromium の Worker で計算した分布とも、抜き取りで一致する（V8 の版の違いの確認） |
| 既存のテスト | `check-segs.mjs`・`check-dist.mjs`・`check-boost.mjs` が通る |
| 版の違い | `MODEL_VERSION` や `key` が違うファイルは使わず計算する（テストで確かめる） |
| ファイルがない | 範囲外の条件・404・壊れたファイルで、今までどおり計算される |
| 画面 | ヘッドレス Chromium で、範囲内の条件は「計算中」を出さずにすぐ表示され、範囲外は従来どおり計算される。コンソールにエラーが出ない |
| 時間 | ワークフロー全体の所要時間を変更前（直近: 29秒〜73秒）と比べる |

実装後に `design-v1.9.md` と README.md・checker/README.md に作り・ローカルでの事前計算の手順・検証結果を記す。

## 8. 確認したいこと

1. **対象範囲**: 案1（Lv.60 だけ、推奨）でよいか。Lv.50・70・80 をよく使うなら案2・3。
2. **よく使う条件**: 既定から変えることが多い設定はあるか（たとえばチケットなし・ヒーラーなし・3時間ごと）。多いものがあれば、その設定を範囲に足すかを決めたい（1項目を2通りにすると件数とサイズはおよそ2倍）。
3. **形式**: gzip した `.json.gz` を置き、`DecompressionStream` で戻す方法でよいか。gzip しない `.json` にすると、案1でも公開物が 64MB になる（転送は Pages の圧縮で小さくなる見込み）。
4. **サイズの目安**: 「公開物（gzip 後）で数十MB以内」と読み替えてよいか。未圧縮の合計で数えると案1（64MB）も超える。
5. **CI**: 毎回計算（A）でよいか。
6. **範囲外の話（今回は変えない）**: 今の IndexedDB のキーに `BUILD` が入っているため、公開のたびに保存済みの分布が使えなくなる。事前計算の範囲内は公開直後もファイルから読めるようになるが、範囲外の条件は公開のたびに計算し直しになる。`BUILD` を外すかどうかは別の版で扱う想定。
