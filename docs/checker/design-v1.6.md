## 2. 計算の高速化

### 2.1 所持数の遷移の使い回し（`fillCurve`）

所持数0からおてつだいを1回ずつ重ねたときの所持数の分布は、所持数の上限・食材確率・きのみの個数・食材配列の個数だけで決まり、おてつだいの回数には依らない。これまでは回数（おてつだいの速さ・げんきで変わる小数）ごとに最初から計算していた。

`fillCurve(cap, ingP, berry, amts)` は、その組ごとに遷移を1つだけ持ち、必要な回数まで伸ばしながら次の累積値を記録する。

- `open[j]`: j 回後に満タンでない確率
- `got[i][j]`・`ings[j]`: 拾った食材の期待個数（スロットごと・合計）
- `berries[j]`: 拾ったきのみの期待個数

区間の値はこの累積値から読む。スキルタイプの抽選回数の分布は `open` の差（j 回目で満タンになる確率）から、食材タイプの食材の個数は `got` から、きのみタイプのきのみ・食材の個数は `berries`・`ings` から求める。回数の小数部分を前後の整数回で混ぜる規則は変えない。区間の結果は、遷移ごとに回数をキーにして使い回す（`cached`）。これで文字列のキーを作る時間もなくなる。

遷移の数の上限とメモリは4章。

### 2.2 lo 回と lo + 1 回の計算の共有

`segRolls` は lo 回と lo + 1 回の `nightRolls` を別々に最初から計算していた。どちらも同じ遷移の途中までなので、`fillCurve` の上では追加の計算がない。

### 2.3 サブスキルの組の確率（`subsetDist`）

効果は選んだサブスキルの組で決まり、選んだ順番には依らない。これまでは順番をすべて数え上げていた（5枠で約74万通り、0.73秒）。1枠ずつ「今持っている組」ごとの確率を積み上げる形にした（5枠で6,188組、0.03秒）。抽選の規則（色を選び、その色の未所持から均等に選ぶ）は同じ。組の数（5枠で1,456）は変わらない。

### 2.4 その他

- `stockSkills` の q の k 乗を、k を1つ進めるたびに q を掛けて求める。
- `amountPatterns`・`allArrs` をポケモンごとに1回だけ作る（計算のたびに作り直していた）。
- 同等以上の確率と順位は、分布が高い順に並んでいることを使って、累積確率と二分探索で求める（記録の一覧で1件ごとに分布の全行を見ていた）。

## 3. 画面

- 先読みはこれまで、今の条件のほかに対象レベル3種 × チケット2種の6条件を計算していた。計算が速くなったので、今の条件とチケットを切り替えた条件だけにする（端末の電池と発熱を抑える）。
- ポケモンや条件を変えたとき、別の条件の計算中なら Worker を止めて作り直し、今の条件から計算する（これまでは前の計算が終わるまで待っていた）。分布を送った後の保存中には止めない。
- 見出し・ポケモンの情報・性能の行の枠は、タイプとポケモンが変わったときだけ作り直す。

## 4. メモリ

計算エンジンは途中の値（1日の値・区間の結果・所持数の遷移）をキャッシュし、これまで捨てていなかった。Worker は1つのエンジンを使い続けるので、5枠の分布を計算するたびにメモリが増える。3タイプ・24条件の5枠の分布を続けて計算すると、変更前は 1,222MB、`fillCurve` を入れただけでは 1,121MB になった（エンジンの値のキャッシュが約740MB、区間と遷移のキャッシュが約340MB）。

- Worker は分布ごとに新しいエンジンを作り、計算が終わったら `clearCaches`（`engine.js`）で区間と遷移のキャッシュを捨てる。分布は画面側に送り、IndexedDB に保存するので、Worker には残さなくてよい。サブスキルの組の分布（`subsetDist`）は小さいので残す。
- 所持数の遷移は、画面側で使い続けても増えすぎないよう、5,000組を超えたらすべて捨てる（1回の分布計算で300〜1,000組）。

同じ24条件で、分布を手元に残したままでも 84MB になった。

- `tests/check-dist.mjs`: 6ケース OK。分布の全行で、二分探索の順位・同等以上の確率が全行を見て数えた値と一致する（確率は完全一致）ことを足した。
- `tests/compare-values.mjs`: 8,000件 OK。きのみ・食材タイプは完全一致、スキルタイプは最大絶対差 5.3e-15（`stockSkills` の累乗の求め方の違い）。
- 分布: 3タイプ10条件（3〜5枠、受け取り・発動回数・ヒーラー・チケットを変えたもの）で、行数と無補正比が完全一致、確率の差は最大 1.1e-16、同等以上の累積確率の差は最大 2.4e-15。`MODEL_VERSION` は上げない。
- ブラウザ（Chromium）: 3タイプで入力・記録・チケットの切り替え・タブの連続切り替えを変更前と同じ手順で行い、結果の帯・性能の行・内訳・計算条件・記録の表示がすべて一致した。同じ手順にかかった時間は14.5秒から5.5秒になった。
